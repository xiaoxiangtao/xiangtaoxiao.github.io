Deploying OpenClaw#

Server and system setup#

Tencent Cloud Lighthouse instance: 4 CPU cores, 4GB RAM, 70GB system disk

Ubuntu 22.04.5 LTS 64-bit — ChatGPT recommended this as the most compatible option.

Installing OpenClaw#

Update the system and install dependencies#

# Update the system
sudo apt update && sudo apt upgrade -y
# Install base dependencies
sudo apt install -y git curl wget unzip build-essential
# Install nvm
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
source ~/.bashrc
# Install Node.js
nvm install --lts
nvm use --lts
# Verify the install and check versions
node -v
npm -v

Install OpenClaw#

npm install -g openclaw@latest

Start OpenClaw#

# Initialise config and install
openclaw onboard --install-daemon
# install-daemon registers the OpenClaw Gateway as a background daemon: it runs
# silently, starts on boot, and restarts itself if it crashes

Accessing the web UI remotely#

Run this on your local machine’s command line, then open 127.0.0.1:18789 in your browser.

My first impression of the web UI for configuration wasn’t great — it’s clearly built for developers, not for casual users. The settings aren’t self-explanatory and there’s no inline help — for example, to configure the LLM API you have to type raw JSON into a text box, with no documentation on the expected format anywhere in sight. The TUI is honestly much easier to use.

# Open an SSH local port-forwarding tunnel, so a service running on the remote
# server is reachable from your own machine over the encrypted SSH channel.
ssh -N -L 18789:127.0.0.1:18789 your-username@your-server-ip

Setting up the agent#

First contact: bootstrapping#

Inside .openclaw/workspace there’s a BOOTSTRAP.md file. The first time you talk to the agent through the TUI, the LLM reads this file first, follows its instructions to work out who it’s supposed to be through the conversation, then rewrites files like agent.md and deletes BOOTSTRAP.md.

Worth noting: talking to the agent directly through the QQ bot does NOT trigger bootstrapping — you need to go through the TUI or the web UI for that.

Sub-agents and multi-agent setups#

You can set up the main agent to spin off a sub-agent for complex, time-consuming tasks, and have it report the result back — which saves both tokens and time.

  • Sub-agents are non-blocking: the main agent doesn’t wait for them and can keep talking to the user, and once the sub-agent finishes, it reports its result back and the loop closes.
  • A sub-agent runs in its own session and doesn’t inherit the main agent’s context or SOUL.md, which is what saves tokens.
  • Think of a sub-agent as a temp worker: it runs its task in the background and hands the result back once it’s done.
  • Good fit for long tasks, parallel tasks, and specialized work.

You configure SOUL.md to tell the main agent when to spin up a sub-agent, and give the sub-agent its own prompt to define its identity and rules so it can do its specific job well.

You can also run multiple long-lived agents in parallel, each with its own workspace, memory, SOUL.md, and session.

  • Useful for setting up multiple long-term “personas” — one that only writes code, one that only does research — each with its own memory and identity.
  • Each can have different permissions, different models, and different messaging channels (WeChat vs. QQ).

Context window settings#

My first impression: this thing burns through tokens fast. Even a simple exchange can cost tens of thousands of tokens, and if you’re using a weaker LLM that gets stuck in a reasoning loop, token usage can spike into the millions for a single hard task.

Set the context window size based on what the model can actually handle — for example, MiniMax 2.5 natively supports a 200k context window. A bigger context window makes the conversation flow better and cuts down on how often the system needs to compress information.

Trying out skills#

Time management with a Notion database#

https://clawhub.ai/xiangtaoxiao/notion-time-management-matrix

I built this on top of a Notion database template I’d already made (a four-quadrant time management matrix) as the data source, with OpenClaw hitting it through the Notion API. You add or close to-dos over WeChat chat, get automatic reminders as deadlines approach, and can pull related files/info and update progress on a task. See the Notion skill docs for the actual API calls.

  • What’s better about this than the traditional way of doing it? Chatting over WeChat feels a lot more natural, and an AI assistant can add a bit of emotional warmth to it too 🐶
  • Honestly, just keeping everything inside OpenClaw itself works the best functionally — the trade-off is you lose a nice-looking interface, and you need to guard against the LLM being flaky and corrupting your data.
  • You can use OpenClaw’s own cron jobs to periodically check to-dos and send reminders. Under the hood, cron is just firing off an instruction to the AI through a specific session at a specific time.

Problems I ran into#

  1. TRAE doesn’t follow OpenClaw’s conventions: fixed it by giving the agent a link to the OpenClaw skill docs and having it read them.
  2. After installing the skill, the agent didn’t pick it up: added a prompt in TOOL.md telling the AI explicitly to use this skill, and also explicitly asked for it on the first message of a conversation. As for why the agent doesn’t automatically trigger the skill by semantic matching once it’s installed — my guess is OpenClaw’s system prompt or the agent’s own prompt already has a default way of handling to-dos baked in, and that takes priority.
  3. Skill status shows “not ready”: run the command below to see which requirement isn’t met, then fix it. openclaw skills check
  4. Hard to debug — no visibility into the agent’s reasoning or tool calls: installed Clawmetry to fix this.
  5. The system mangled a path — extra spaces, wrong characters — so the command wouldn’t run. I asked GPT and made two fixes: renamed the skill’s folder to swap - for _, and added ./script/ to the path in the prompt. After that it worked cleanly — the AI didn’t need to retry, it just ran successfully.
  6. The AI’s task logic isn’t always very rigorous — I ran into a case where it acted purely from memory instead of reading the actual status file. In theory that’s the “smart” move, but if the prompt doesn’t require it, the AI won’t reliably notice when things have changed. (This was with MiniMax 2.5.)
  7. OpenClaw’s built-in memory isn’t great — right now the memory file has picked up a lot of unimportant, even outright wrong, content, and it’s badly polluting the context. Sometimes even when I explicitly point out an error and ask it to remember the correction, it still doesn’t get written to the memory file.
  8. Maybe worth trying calling the Notion API directly (i.e. the Notion skill) and customizing it so the AI understands what each database is for and how it’s structured — could that get me synced to-do and knowledge-base management?

Lessons learned#

Prompt tricks that worked:

  1. Stop the AI from improvising: point it at the official docs and have it read them first, then explicitly forbid it from deviating from what the docs specify.
  2. Stop the AI from only fixing things locally instead of thinking about the whole picture.
  3. Work around some models being bad at handling tokens like - and at concatenating instructions correctly: different models — and different temperature settings — vary a lot in how reliably they build paths and system commands. When that’s unstable, it’s better to hard-code the command as a tool and have the AI just call the tool with its output. This will probably get better as LLMs improve.
  4. Stop the AI from always acting on memory: OpenClaw does have a memory structure, but if some key piece of data changes and the AI still acts on what it remembers instead of the current state, that leads to failures or corrupted updates. For anything that’s a critical setting, it’s better to require the AI to read the actual config file rather than pull it from context or memory — especially while debugging.
